# 子 Agent 使用說明

這個檔案說明在本專案裡什麼時候應該開子 Agent、怎麼開、怎麼驗收。

核心原則：主 Agent 負責方向、拆分、整合和最終判斷；子 Agent 只負責邊界清楚、輸入明確、結果可檢查的小任務。

## 什麼時候可以開子 Agent

適合開子 Agent 的情況：

- 任務可以拆成互不影響的小塊。
- 每個小塊都有明確輸入、明確目標和明確完成標準。
- 子 Agent 只需要檢視或修改少量檔案。
- 子 Agent 的結果可以透過檔案、測試、日誌、截圖或 Godot 復現步驟檢查。
- 多個任務之間不會同時修改同一個指令碼、同一個場景或同一個檔案。

常見適合任務：

- 檢查某個目錄或模組的當前狀態。
- 對照 spec 檢查某個功能有沒有實現。
- 按主 Agent 指定範圍實現一個獨立功能。
- 為一個獨立功能設計測試用例。
- 調查一個失敗測試、報錯或日誌問題。
- 檢查 Godot 場景、指令碼和資源引用是否一致。
- 對照畫面基準和真實截圖做視覺驗收。
- 複核實現是否滿足驗收標準。
- 複核程式碼質量和專案結構是否符合本專案規則。

## 什麼時候不要開子 Agent

以下情況不要急著開子 Agent：

- spec 還沒讀清楚，驗收標準還沒定。
- 任務邊界很模糊，只知道“大概做一個功能”。
- 任務需要決定玩法規則、數值邊界、產品取捨或目錄結構。
- 多個子任務都會改同一個 `.gd`、`.tscn`、`.tres` 或同一個檔案。
- 當前工作區有未確認的本地改動，可能被子 Agent 覆蓋。
- 還沒有測試、日誌、截圖或復現步驟，無法判斷結果是否正確。
- 問題看起來分散，但很可能來自同一個根因。

如果任務不清楚，主 Agent 要先自己補上下文，必要時先寫驗收標準和測試方案，再決定是否拆給子 Agent。

## 開子 Agent 前必須準備的資訊

主 Agent 派發任務前，要先準備下面這些資訊。不要讓子 Agent 自己猜。

- 本次任務來自哪個 spec 或哪條使用者要求。
- 本次任務對應哪些驗收標準。
- 子 Agent 的具體目標是什麼。
- 子 Agent 可以檢視哪些檔案。
- 子 Agent 可以修改哪些檔案。
- 子 Agent 不能修改哪些檔案。
- 完成後必須返回哪些內容。
- 用什麼方式驗證結果。

如果是開發任務，還要說明：

- 是否允許修改 Godot 場景。
- 是否允許新增資源。
- 是否允許改測試工具。
- 是否必須提供截圖、日誌或測試輸出。

如果是視覺校對任務，還要說明：

- 要對照哪份畫面基準、素材說明或參考截圖。
- 要檢查哪張真實執行截圖、哪段幀序列或哪段錄屏。
- 本次重點看 HUD、升級介面、結算介面、戰鬥場景還是 VFX。
- 缺少哪些證據時必須判為不透過。

## 子 Agent 任務寫法

給子 Agent 的任務要小、清楚、可檢查。

推薦寫法：

```md
任務：檢查玩家移動邏輯是否滿足驗收標準。

背景：
- 專案是 Godot 4.x + GDScript 2D 遊戲。
- 當前驗收標準在 `docs/player-movement-acceptance.md`。

範圍：
- 可以讀取 `scripts/player_controller.gd` 和相關測試檔案。
- 不要修改程式碼。
- 不要修改場景。

目標：
- 對照驗收標準逐條檢查。
- 列出已滿足、未滿足和無法判斷的專案。

返回：
- 簡短結論。
- 逐條檢查結果。
- 需要主 Agent 決定的問題。
```

開發任務可以這樣寫：

```md
任務：實現升級卡片彈窗的執行時 UI。

背景：
- spec 在 `spec/v0.1-傳奇倖存者-歷史原型.md`。
- 驗收標準在 `docs/development/acceptance-standard.md`。
- 測試用例在 `docs/v0.1-test-cases.md`。

範圍：
- 可以修改 `scripts/`、`scenes/` 和必要的 `assets/` 執行時資源。
- 不要修改驗收標準。
- 不要修改測試口徑。
- 不要重構無關玩法邏輯。

目標：
- 升級三選一居中彈出，戰場壓暗。
- 卡片結構對齊畫面基準。
- 提供真實執行截圖或幀序列。

返回：
- 改了哪些檔案。
- 如何執行驗證。
- 哪些驗收標準被覆蓋。
- 是否還有沒覆蓋的測試點。
```

視覺校對任務可以這樣寫：

```md
任務：對照基準圖複核升級三選一介面。

背景：
- spec 在 `spec/v0.1-傳奇倖存者-歷史原型.md`。
- 驗收標準在 `docs/development/acceptance-standard.md`。
- 畫面基準是 `docs/references/upgrade-baseline.png`。
- 真實執行截圖是 `reports/visual/upgrade-current.png`。

範圍：
- 只讀。
- 不要修改程式碼、場景、資源或檔案。

目標：
- 對照基準檢查彈窗位置、戰場壓暗、三卡比例、卡片結構、裝飾層級、材質風格和文字可讀性。
- 按 P0/P1/P2 列出視覺問題。

返回：
- 透過 / 不透過。
- 每個問題對應哪條驗收標準或哪張基準圖。
- 缺少哪些截圖、幀序列或觀察證據。
```

不要這樣寫：

- “把整個功能做完。”
- “檢查一下有沒有問題。”
- “最佳化所有程式碼。”
- “根據 spec 全部實現。”

這些任務太大，子 Agent 容易跑偏。

## 推薦協作流程

如果要讓子 Agent 參與開發，主 Agent 按這個流程走：

1. 主 Agent 先閱讀 spec。
2. 主 Agent 寫出或確認驗收標準。
3. 主 Agent 寫出或確認測試用例。
4. 主 Agent 判斷哪些任務可以獨立拆分。
5. 主 Agent 給每個子 Agent 一份完整、邊界清楚的任務說明。
6. `builder` 完成實現後，主 Agent 先複核是否滿足驗收標準。
7. 涉及畫面的改動，先交給 `visual-reviewer` 對照真實截圖和基準圖做只讀複核。
8. 驗收標準和必要的視覺複核透過後，再交給 `reviewer` 做綜合複核。
9. 如果發現問題，主 Agent 明確指出問題，並安排修復。
10. 所有子任務完成後，主 Agent 統一執行測試或檢查。
11. 最終彙報由主 Agent 給出，不直接照搬子 Agent 結論。

## 並行規則

可以並行的情況：

- 多個子 Agent 都是隻讀調查。
- 多個子 Agent 檢查不同目錄、不同檔案或不同失敗點。
- 多個任務之間不會修改同一批檔案。
- 每個任務都有獨立驗證方式。

不要並行的情況：

- 多個子 Agent 會修改同一個指令碼。
- 多個子 Agent 會修改同一個 Godot 場景。
- 多個子 Agent 會同時改 `docs/index.md`、AGENTS.md 或同一份 spec。
- 一個任務的結果會決定另一個任務怎麼做。
- 當前問題可能來自同一個根因，需要先統一分析。

並行任務結束後，主 Agent 必須統一檢查改動，確認沒有互相覆蓋、重複實現或風格不一致。

## 子 Agent 返回格式

子 Agent 完成後，必須用簡短清單返回：

- 做了什麼。
- 改了哪些檔案。
- 怎麼驗證。
- 是否完全滿足任務要求。
- 還存在哪些不確定點或風險。

如果沒有完成，必須說明：

- 卡在哪裡。
- 已經查過什麼。
- 為什麼繼續不下去。
- 需要主 Agent 補什麼上下文。
- 下一步建議怎麼做。

## 複核規則

主 Agent 不能只相信子 Agent 的結論。至少要做這些複核：

- 檢查子 Agent 是否超出任務範圍。
- 檢查是否改了不該改的檔案。
- 對照驗收標準逐條確認。
- 對照測試用例確認覆蓋情況。
- 檢視關鍵 diff，確認沒有順手重構無關內容。
- 執行相關測試、檢查指令碼或 Godot 驗證步驟。
- 如果改了檔案，確認 `docs/index.md` 已更新。

如果子 Agent 做的是程式碼實現，主 Agent 要先做驗收標準複核，再做程式碼質量複核。驗收標準沒過之前，不進入程式碼質量複核。

如果子 Agent 做的是畫面實現，主 Agent 要先確認有真實截圖、幀序列或錄屏，再交給 `visual-reviewer`。沒有可觀察證據時，不進入視覺透過判斷。

## Godot 專案特別規則

- 不得替換 Godot 作為遊戲主體。
- 不得把核心遊戲邏輯搬到外部指令碼裡。
- 修改 `.tscn`、`.tres`、資源引用或 Godot 匯入檔案時，必須說明影響範圍。
- 涉及畫面、碰撞、輸入、關卡狀態或資源載入時，必須提供可觀察的驗證方式。
- 外部指令碼只能用於資源處理、檢查和輔助驗證，不能承載核心遊戲邏輯。
- 場景和指令碼改動要儘量小，不要順手重構無關內容。

## 一句話判斷

開子 Agent 前先問一句：這個任務能不能用清楚的範圍、輸入、輸出和驗證方式交代明白？

如果答案是能，可以開。

如果答案是不能，主 Agent 先把問題拆清楚。
