# Harness 原則整理

本文整理兩篇 harness 文章中對本倉庫有用的原則，並把它們改寫成《傳奇倖存者》開發時可執行的規則。

來源：

- OpenAI, [Harness engineering: leveraging Codex in an agent-first world](https://openai.com/index/harness-engineering/), 2026-02-11
- Anthropic, [Harness design for long-running application development](https://www.anthropic.com/engineering/harness-design-long-running-apps), 2026-03-24

> **版本適用：** 本文將 Harness 流程套用至現行《傳奇倖存者》v0.2；過往 v0.1 限制若與科幻玩法規格衝突，應以現行規格和適用 SF 驗收條款為準。

## 核心判斷

Harness 不是一個更長的提示詞，而是一套讓 AI 代理能持續做正確工作的環境：清楚的目標、可讀的倉庫知識、可執行的驗收標準、可觀察的執行狀態、能失敗的測試、真實畫面證據，以及能把錯誤沉澱回倉庫的反饋迴圈。

對本專案來說，harness 的目標不是讓代理一次性寫出更多程式碼，而是讓代理每次都能知道：

1. 現在要做的最小閉環是什麼。
2. 哪些範圍明確不做。
3. 遊戲執行時的真實狀態如何讀取。
4. 功能、美術、音訊和 UI 是否真的達標。
5. 失敗時要補哪種工具、檔案、規則或測試。

## 原則清單

### 1. 人負責方向，代理負責執行和取證

人類要定義目標、邊界、驗收口徑和主觀取捨；代理負責拆任務、寫程式碼、跑檢查、儲存截圖、記錄證據和修復失敗。

當代理卡住時，不要只讓它“再試一次”。應該問：缺的是可讀狀態、明確規則、測試入口、素材說明、執行截圖，還是更具體的完成標準。

### 2. 倉庫是事實來源

對代理不可見的知識，等於不存在。遊戲規則、素材接入、驗收標準、測試命令、經驗規則和交付記錄都應寫入倉庫，而不是隻留在聊天記錄、外部檔案或人的記憶裡。

`AGENTS.md` 應作為入口目錄，指向更深的檔案；不要把所有細節塞成一個巨大手冊。長檔案要拆成穩定主題，並讓代理按任務需要逐步讀取。

### 3. 先讓系統可觀察，再擴充套件玩法

複雜任務要先建立反饋迴路。對本專案，優先順序是：

1. 固定 seed。
2. debug 引數。
3. `get_debug_snapshot()`。
4. `get_recent_feedback_events()`。
5. smoke test。
6. 真實截圖、動態幀或可視視窗檢查。
7. 交付記錄和 Experience Library 更新。

沒有這些觀測點，代理會把“程式碼看起來合理”誤判成“遊戲真的可玩”。

### 4. 把大任務拆成可驗收的小塊

長時間開發不能靠一個模糊目標連續推進。每一塊工作都要先寫清楚：

- 本輪要交付什麼。
- 不交付什麼。
- 哪些狀態、事件、截圖或動態幀能證明它完成。
- 哪些 smoke 引數會失敗或透過。

Anthropic 文章裡的 planner / generator / evaluator 結構，可以簡化成當前倉庫的工作方式：先定本輪契約，再實現，再用獨立驗收標準檢查。範圍較大時，把契約寫進檔案或交付記錄，方便下一輪繼續。

### 5. 生成者和評估者要分離

代理很容易高估自己剛完成的工作，尤其是 UI、視覺、手感這類主觀任務。實現完成後，驗收要站在“挑錯”的角度執行，而不是讓同一段總結文字自我認可。

本專案的評估者至少要檢查：

- 功能是否真實跑通。
- UI/VFX 是否使用定製資產，而不是佔位圖或原素材切片。
- 逐控制元件相似度和完成度是否都達到 0.90。
- 動態幀裡是否有遮擋、重疊、裁切、跳位或不可點選。
- 音訊是否真實載入並在事件中觸發。

### 6. 把主觀質量變成可評分標準

“好看”“有手感”“像參考圖”不能直接作為驗收。要把它們拆成可記錄的標準：

- 參考 crop。
- 視覺特徵拆解。
- 最終資產路徑。
- 執行截圖 crop。
- 並排對照圖。
- `style_similarity_score`。
- `asset_completion_score`。
- 動態幀觀察結論。

這和 Anthropic 文章中把前端審美拆成設計質量、原創性、工藝和功能性相同：主觀判斷不能完全消失，但必須被拆成代理能執行、能複查的檢查項。

### 7. 驗證必須操作真實應用

程式碼審查和 headless smoke 只能證明一部分事實。涉及 UI、佈局、動畫、特效、音訊和玩法手感時，必須讓代理啟動真實遊戲或可渲染畫面，儲存截圖、frame dump 或短錄屏。

本專案不能只用控制元件座標、日誌或 “SMOKE_TEST_PASS” 宣稱 UI 完成。真實畫面裡有遮擋、裁切、預設控制元件、特效壓住 UI 或中文文案不一致時，驗收失敗。

### 8. 用硬邊界保護架構和範圍

代理適合在明確邊界內高速執行，不適合在邊界模糊時自行擴大產品。倉庫應機械地或檔案化地守住這些邊界：

- 遊戲規則不寫死在 UI、動畫或特效指令碼裡。
- 輸入、戰鬥、刷怪、升級、結算分開。
- 不引入後端、資料庫、賬號、排行榜或多人聯機。
- 不擅自擴充未獲核准的劇情、商店、揹包、多地圖、多人或後端；現行 v0.2 已核准主選單、首領、存檔與永久成長，不可沿用 v0.1 的禁止清單。
- 素材只能使用當前工作樹內的檔案、素材和程式碼。

架構規則應儘量透過測試、指令碼、資源審計和清晰錯誤資訊執行；不能只靠口頭提醒。

### 9. 長任務需要結構化交接

當任務跨多輪、上下文變長或需要暫停時，必須把當前狀態寫入倉庫內的交付記錄、實驗日誌或計劃檔案，至少包含：

- 已完成的驗收項。
- 未完成的驗收項。
- 已跑命令和結果。
- 關鍵截圖或動態幀路徑。
- 發現的問題。
- 下一步最小任務。

上下文壓縮或新會話不是問題，問題是沒有足夠清楚的交接檔案讓下一輪代理接住工作。

### 10. Harness 複雜度要定期清理

每個 harness 元件都代表一個假設：當前模型自己做不好這件事，所以需要額外腳手架。模型、專案和工具變了之後，這個假設可能失效。

因此不要盲目增加流程。新增測試、檔案、評估代理、截圖門禁或指令碼前，要說明它解決了什麼實際失敗。後續如果它不再提供價值，應刪除、合併或簡化。

### 11. 錯誤要沉澱成規則

代理會複用倉庫裡已有模式，壞模式也會被複制。解決過的問題不能只留在最終回覆裡，應該寫入：

- `docs/experience-library/lessons.md`：完整記錄現象、原因、修復、驗證和下次規則。
- `docs/experience-library/active-rules.md`：容易復發的問題提煉成短規則。

這相當於把一次人工判斷轉成後續每輪都能讀取的約束。

## 本倉庫的預設工作流

每輪開發按下面順序執行：

1. 按 `AGENTS.md` 讀取上下文。
2. 明確本輪最小目標和不做範圍。
3. 寫清楚本輪驗收入口：命令、狀態欄位、反饋事件、截圖或動態幀。
4. 先補缺失的可觀測性，再擴充套件玩法或視覺。
5. 實現一個小塊後立即執行可用檢查。
6. UI/VFX/音訊相關改動必須儲存真實畫面或事件證據。
7. 失敗時補工具、測試、檔案或規則，不用猜測替代驗證。
8. 解決過的問題寫入 Experience Library。
9. 提交前只 stage 本輪相關檔案，並執行 `git diff --check`。

## 不要做的事

- 不把參考文章改寫成一篇長理論檔案後就停止。
- 不把所有規則繼續堆進 `AGENTS.md`。
- 不用聊天記錄代替倉庫檔案。
- 不用 headless 輸出代替 UI/VFX 的真實畫面檢查。
- 不讓實現者只靠自我總結判定透過。
- 不為了讓測試透過而降低驗收標準。
- 不在缺少 seed、snapshot、事件和截圖能力時擴充套件更多玩法。
- 不在沒有明確失敗案例時增加複雜 harness 元件。
